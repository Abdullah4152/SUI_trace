# Data Card

## Purpose

This artifact supports reproduction of a step-level intervention audit over explicit reasoning
traces. It distributes the pipeline that produces that audit, plus the human annotations
collected to validate it.

Generated data — benchmark samples, model traces, intervention records, utility scores, and
revision outputs — is **not distributed**. It is produced by running the pipeline documented in
the README. This card describes the schema of that generated data so it can be interpreted
after a run, and documents the annotation data that *is* included.

## Source Benchmarks

The experiments draw on three public benchmarks, obtained from their official distributions:

- MATH-500
- GPQA Diamond
- LogiQA 2.0

`scripts/prepare_pilot_sample.py` draws the evaluation sample from these under a fixed seed.
Point `dataset_paths` in `config/sui_final_config.json` at your local copies before running it.

## Generated Data

Running the pipeline produces reasoning traces and continuation outputs for three target
models — GLM-5.1, Nemotron-3 Nano Omni 30B Reasoning, and Mistral Medium 3.5 128B — along with
edited-step records produced by the configured editor model and scored by the configured judge
model. Both roles are set in `config/sui_final_config.json`.

Because the models are hosted services, generated data is not bit-reproducible across runs.
Treat each run's outputs as a fresh sample rather than a reconstruction of a previous one.

### SUI utility rows

Written to `pilot_utility_scores.csv` in the SUI output directory.

| Column | Meaning |
|---|---|
| `model` | Target model label. |
| `benchmark` | Source benchmark. |
| `instance_id` | Stable instance identifier. |
| `step_id` | Step index within the segmented reasoning trace. |
| `valid_for_utility` | Whether the edited step passed validity checks and can be used for utility analysis. |
| `delta_ans` | Whether the edited continuation changed the answer. |
| `delta_corr` | Whether the edited continuation changed correctness. |
| `delta_cont` | Continuation divergence score. |
| `utility_score` | Aggregate utility proxy. |
| `step_bin` | Automatic utility category. |

`step_bin` is an **automatic** label derived from the utility signals. It is an analysis
variable, not ground truth, and raters are instructed not to treat it as such.

### Revision rows

Written to `uatr_results.csv` in the UATR output directory. Each row is one method applied to
one instance. Key columns: `method`, `status`, `original_correctness`, `correctness`,
`delta_corr`, `answer_changed`, `calls`, `total_tokens`, `latency_s`.

`correctness` is scored strictly — a missing or unparsed final answer counts as incorrect. Rows
where the model produced no parseable answer are still present with a null prediction, so any
accuracy computed from this file must state whether its denominator is all rows or parsed rows
only. The two differ, and they differ by method.

## Human Validation Data

**This is the only data in the repository that cannot be regenerated by running code.**

`human_validation/human_validation_annotation_sheet_filled.csv` contains independent
annotations from three raters, anonymized as `R1`, `R2`, and `R3`. The design used a
calibration split, annotated first and discussed, followed by an independently annotated main
split. All reported agreement figures come from the main split; calibration items exist to
describe the alignment process only.

Supporting files, all preserved so the annotations remain interpretable even though the SUI run
that produced the items is not distributed:

| File | Role |
|---|---|
| `human_validation_annotation_sheet.csv` | Blank annotation instrument. |
| `human_validation_annotation_sheet_filled.csv` | Completed annotations from all three raters. |
| `human_validation_sample.jsonl` | The exact items presented to raters. |
| `human_validation_metadata.csv` | Item-level metadata linking annotations to source steps. |
| `human_validation_workbook.xlsx` | Spreadsheet form of the instrument. |
| `HUMAN_VALIDATION_INSTRUCTIONS.md` | Annotation protocol and rating scales. |

### Annotation columns

| Column | Meaning |
|---|---|
| `validation_item_id` | Stable annotation item identifier. |
| `split` | `calibration` or `main`. |
| `rater_id` | Anonymized rater id. |
| `valid_intervention_label` | Rater judgment of whether the edit is a valid local intervention. |
| `semantic_change_score` | Ordinal rating of semantic change. |
| `local_coherence_score` | Ordinal rating of local coherence. |
| `fluency_score` | Ordinal rating of fluency. |
| `answer_leakage_label` | Whether the edit leaks the answer. |
| `over_disruption_label` | Whether the edit is too disruptive to isolate step utility. |
| `human_failure_mode` | Primary failure mode when an item is judged invalid or borderline. |
| `comment` | Optional free-text rater note. |

### Provenance requirement

Any claim described as human validation must rest on annotations produced by human raters
following the protocol in `HUMAN_VALIDATION_INSTRUCTIONS.md`. If annotations are generated by
models, simulated from rater personas, or otherwise synthesized, they may be reported only as
an internal dry run and must be labeled as such — never as human validation. Record which
applies to the sheet in this repository before citing it in a paper.

## Reuse Notes

This artifact is intended for anonymous peer review and reproducibility. Before redistributing
outside the review process, check the licenses and redistribution terms of the source
benchmarks and of any model outputs a run produces.
